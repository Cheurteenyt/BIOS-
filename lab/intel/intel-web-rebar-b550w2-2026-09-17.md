## 3. Les recherches approfondies (17 requêtes, 15 pages lues)

### 3.1 La chaîne de détection officielle — NVIDIA (a_id/5165 + communiqué 30-series)
La page officielle du **NVIDIA Resizable BAR Firmware Update Tool** décompose la chaîne en **trois composantes** : (1) **GPU + vBIOS** supportant ReBAR (« Support for a specific sku determined by GPU vendor ») ; (2) **SBIOS** : boot UEFI, « Above 4GB Decoding » activé, « Resizable BAR » activé, **CSM désactivé**, disque en GPT ; (3) **driver** Game Ready avec versions minimales explicites : **RTX 3070 : 461.40+** (comme les 3080/3060 NB), 3060 : 461.72, autres 30-series : 465.89. L'outil classe chaque carte : « Update supported, will be applied » (le vBIOS actuel ne supporte pas ReBAR mais est updatable) / « Already updated » / « ReBAR already enabled » / « Unsupported by this tool, contact card vendor » / « Unsupported ». Le troubleshooting officiel pour un « No » persistant dans le Panneau NVIDIA : vérifier CSM off, mode UEFI/GPT, et **« reconfirm the VBIOS updated successfully »**. Le communiqué (30 mars 2021) confirme que côté AMD, la **500 Series** est officiellement supportée (et la 400 avec CPU Zen 3) — notre B550 est donc dans le périmètre officiel. L'outil a aussi une **version Linux** (`newlinuxupdater`) documentée par NVIDIA sur son forum dev.

### 3.2 L'heuristique Auto ASUS explicitée — ROG Forum
Le modérateur ROG donne la phrase que nos rings cherchaient : « **If when you enable (Auto) Re-Size BAR Support, you get the error message "The VGA card is not supported by UEFI driver." during POST, your issue is GPU VBIOS related.** » Autrement dit : l'Auto ASUS **teste la carte pendant le POST** (module UEFI/GOP du firmware vs vBIOS de la carte) et refuse silencieusement (ou bruyamment) si le vBIOS ne passe pas le test. Le fil documente aussi le contre-cas : une EVGA 3080 FTW3 dont le **switch de vBIOS (profil OC) a cassé ReBAR** — un mauvais vBIOS retire la capacité ; et un utilisateur avec « Above 4G enabled in BIOS » que l'outil OS déclare désactivé — les rapporteurs se contredisent. Checklist ROG complète : CSM Disabled, Secure Boot « Windows UEFI Mode », PCI Subsystem, vérification par NVIDIA Control Panel « System Information » puis GPU-Z onglet « PCIe Resizable BAR ». Dernier fait en résonance avec notre ring 50 : sur une X570 ASUS, un utilisateur confirme l'option n'offre que `Disabled` et `Auto` — **pas d'Enabled** : notre lecture {0x00 Disabled, 0x01 Auto} est une loi ASUS générales, et le conseil communautaire « set enabled, not auto » (TPU, nov. 2025) est donc **inapplicable sur cette carte** : ici, Auto EST la voie d'engagement.

### 3.3 Le cap vBIOS 256 MB — TechPowerUp 330305 (RTX 3070)
Thread (déc. 2024) au symptôme identique au nôtre : « It is enabled in BIOS along with the other necessary settings, but still seems to be disabled when checking in the Nvidia app and GPUZ. » Débats, puis le fait technique décisif (posteur `:D:D`) : « **Some early 30 series came with resizable BAR capped to 256MB. All the VBIOS updates did AFAICT is change that cap (1 nibble) to suit the VRAM Size.** » — le vBIOS porte le **cap de taille de BAR** (champ du capability PCIe Resizable BAR), et les mises à jour vBIOS « ReBAR » ne changent souvent que ce cap. En page 2 (visible dans les extraits moteur) : « Had the same problem, Gigabyte RTX 3070 OC. **Turns out it was a matter of updating the vBIOS.** » Autres enseignements : l'utilitaire ASUS peut refuser de mettre à jour (« Your VBIOS does not need to be updated ») alors que la mise à jour est nécessaire ; certains boards ASUS ont des options « **visually enabled but broken** » que seul un reflash firmware + re-saisie manuelle (pas le profil sauvegardé USB) corrige ; un ancien bug de boards demandait « 4G decoding ON et ReBAR Disabled » (ou l'inverse) pour fonctionner — les **pair laws** peuvent être buggées chez le vendor aussi, ce que nos mesures B550 n'avaient pas besoin de supposer (les nôtres sont cohérentes).

### 3.4 La détection côté Linux / omarchy — ArchWiki + forum dev NVIDIA
Le guide officiel NVIDIA (MarkusHoHo, janv. 2023, RTX 3060 Ti FE, Ubuntu) donne le protocole complet : `nvidia-smi -q | grep -i bar -A 3` — « If this GPU would support Resizable BAR the Total memory would be the whole VRAM size (8192 MiB). That means I need to update the GPU VBIOS. » (BAR1 = 256 MiB ⇒ inactif ; BAR1 = toute la VRAM ⇒ actif). Flash sous Linux : console texte, `rmmod nvidia_drm nvidia_modeset nvidia_uvm nvidia`, outil `newlinuxupdater`, reboot ; pour les cartes OEM, les outils vendor (Windows PE possible). **L'ArchWiki** (section Resizable BAR de « Improving performance ») ajoute : `journalctl -k --grep=BAR=` qui doit montrer `[drm] Detected VRAM RAM=8176M, BAR=8192M` ; `lspci -vv -d ::03xx | grep BAR` montrant « **Physical Resizable BAR** » avec `current size` vs `supported` (16MB/…/16GB) — exactement la chaîne de vérification que notre day-0 report a ancrée au ring 49 ; un **power cycle complet** peut être requis pour que le redimensionnement prenne effet ; et pour NVIDIA **Blackwell**, le driver n'active pas ReBAR automatiquement : `options nvidia NVreg_EnableResizableBar=1` + initramfs. Notre `diag-gpu` implémente déjà la règle BAR1 ≤ 256 MiB ⇒ « Resizable BAR likely disabled » (le rendu `gpu-bar1-small`) — il est conforme à la pratique canonique.

### 3.5 L'écosystème « ce qui n'existe pas » — ReBarUEFI
Le projet communautaire `xCuri0/ReBarUEFI` (2,4 k étoiles) est un **pilote DXE** qui apporte ReBAR « to (almost) any UEFI system ». Mécanisme exact (README) : le module ReBarDxe est injecté dans le volume DXE du firmware et **remplace la fonction `PreprocessController` du `PciHostBridgeResourceAllocationProtocol`** — après avoir appelé l'originale, il lit la capacité Resizable BAR de la carte et force la taille indiquée dans la **variable NVRAM `ReBarState`** (écrite par l'outil userland ReBarState, disponible sous Linux via CMake) ; le `PciBus` détecte la nouvelle taille pendant l'énumération PCI et l'alloue. La communauté a donc fabriqué **le module que le vendor ASUS garde enfermé dans son pont de 4,25 Mo** (notre Front E du ring 52) : même architecture (une variable NVRAM + un exécuteur DXE), mais variable exposée et heuristique remplacée par un choix explicite. Son wiki « Common issues » documente la loi quantifiée que nous avions mesurée côté IFR : **sans 4G decoding, ReBAR plafonne à 1 GB** (parfois 512 MB ; TOLUD réduit peut donner 2 GB) ; « Driver shows ReBAR disabled while GPU-Z shows it working → réinstaller le driver » ; « **GPU-Z often reports 4G decode/CSM incorrectly** » ; « RTX 30 series : a VBIOS update is required » ; stutters Ryzen = firmware bug référencé (gitlab amd #1864) ; la palette UEFIPatch (limit removal 4/16/64 GB, « prevent 64-bit BARs from being downgraded to 32-bit », MMIO 512 GB/39-bit pour Skylake..Coffee Lake et Haswell/Broadwell) ; et `NvStrapsReBar` pour les Turing. À noter pour notre doctrine : tout cela est **patch territory** — documenté, jamais appliqué ici.

### 3.6 Les modes de défaillance « flip » et cousins
Les recherches ont aussi capté les défaillances voisines de notre symptôme : « Above 4G decoding » qui se re-désactive tout seul au reboot quand le dGPU n'a pas de legacy ROM (WinRAID) ; « CSM Support automatically re-enables itself » (Tom's Hardware, août 2026) ; menu CSM qui disparaît après avoir désactivé CSM + activé Above 4G (ASRock) ; Windows qui ne boote plus avec Above 4G en mode mixte MBR/Legacy (Microsoft Learn : être en UEFI pur). Notre live mesuré (Above4gDecode 0x01, CsmSupport 0x00) est stable et cohérent — aucun de ces modes de flip ne correspond à notre carte.

## 4. Cartographie vers nos rings — qui peut dire « détecte mal » ?

Nos rings 46-52 ont mesuré **côté firmware ASUS** : l'axe complet (Above4gDecode 0x1BA / ResizeBarSupport 0x1BB / Sriov 0x1BC / Csm 0x1F2), le langage (ReBAR = {0x00 Disabled, **0x01 Auto**} — pas d'Enabled), la loi d'usine (toute la chaîne décode expédiée OFF, 15/15 croisements de sources), la grammaire (le C-source embarqué nomme chaque octet), la cour (34 lecteurs, le pont de 4,25 Mo identifié et release-invariant). Le firmware est **cohérent et propre** : l'usine livre OFF, l'utilisateur a écrit 0x01 (Auto est un état écrit, pas l'état d'usine), l'help du vendor documente trois conditions (64-bit decoding, CSM off, GPU ReBAR-capable). L'intelligence web s'assemble par-dessus sans contredire un seul de nos octets, et **renforce le candidat GPU/vBIOS** : l'heuristique Auto ASUS teste le vBIOS pendant le POST (ROG forum), les premières RTX 30 (dont GA104) ont un vBIOS capé à 256 MB qu'une mise à jour débloque (TPU + outil NVIDIA officiel), et la détection côté Linux lit ce résultat (BAR1 vs VRAM). Les trois familles candidates du day-0 report restent, mais re-pesées : (a) **vBIOS GPU sans flag/cap ReBAR** — favorisé par l'intel et par le thread TechPowerUp fourni par le fondateur ; (b) heuristique Auto dans le pont 4,25 Mo — bornée, non lue, doctrine interdisant le patch ; (c) demi OS/driver — versions minimales driver (3070 : 461.40+), `NVreg_EnableResizableBar=1` (Blackwell seulement), désaccords GPU-Z/driver, power cycle manquant. Ce que le dump du 16/09 tranchera : le delta live-minus-factory de la variable Setup, octet par octet, en noms de champs. Ce qu'il ne tranchera **pas** : l'état du vBIOS de la carte GPU — pour cela, la voie canonique est côté OS (`nvidia-smi -q | grep -i bar`, `lspci -vv`, version driver, et l'identité exacte de la carte/vBIOS à comparer avec la base TechPowerUp).

## 5. Actions suggérées (aucune ne touche au firmware)
1. Côté OS de la machine du fondateur : `nvidia-smi -q | grep -i bar -A 3` (BAR1 = 256 MiB ou VRAM complète ?), `lspci -vv` (Physical Resizable BAR, current/supported), version du driver (≥ 461.40 pour une 3070).
2. Identifier la carte exacte et son vBIOS (`nvidia-smi -q | grep -i "VBIOS Version"` ou GPU-Z) et le comparer à la base vBIOS TechPowerUp — un vBIOS pré-mars-2021 ou capé 256 MB est le suspect n° 1 d'un « Auto détecte mal ».
3. Power cycle complet (extinction électrique) avant tout verdict — l'ArchWiki le documente comme requis dans certains cas.
4. Garder le diagnostic firmware pour le dump 16/09 (le protocole day-0 inchangé) — et ne pas flasher quoi que ce soit sans le protocole complet de sauvegarde/restauration (doctrine inchangée).
5. Le post overclockers.ru mort : si le fondateur a le lien du topic parent (`t=`), le re-fetch devient possible — sinon classer définitivement.
